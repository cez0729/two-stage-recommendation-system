# 推荐系统新增实验：跨品类复现、GRU 对照与扩展性

这份文件补充原研究报告。原 Video Games 结果、Docker 服务版本和发布包继续保留。
本轮的目标是增加可以核查的研究证据，而不是为了提高分数修改测试集或强行替换模型。
完整复现命令及方法边界见[英文实验报告](extension_study_en.md)。

## 一、为什么选择这三项改进

与 RecBole 等公开推荐研究框架相比，我们之前主要缺少三个方面：
在另一个商品品类上的完整实验、不同神经网络历史编码方式的对照、以及多进程和大目录的扩展性测量。
这三项分别补充可推广性、模型分析能力和工程实验能力。

这里借鉴的是公开项目的研究方法，不是直接比较它们的排行榜分数。
数据过滤、切分方法、候选数量和负样本协议不同，分数不能直接横向比较。
公开参考包括 [RecBole](https://github.com/RUCAIBox/RecBole)、
[GRU4Rec](https://github.com/hidasib/GRU4Rec)、
[FAISS](https://github.com/facebookresearch/faiss) 和
[Uvicorn](https://www.uvicorn.org/deployment/)。

## 二、第二个公开数据集

选择 Amazon Reviews 2018 的 Musical Instruments（乐器）品类。
原 Video Games 和新数据来自同一个公开数据源，因此这是跨品类复现，
不能称为跨平台或跨独立数据源验证。

下载来源：

- [乐器 5-core 评论数据](https://mcauleylab.ucsd.edu/public_datasets/data/amazon_v2/categoryFilesSmall/Musical_Instruments_5.json.gz)
- [乐器商品元数据](https://mcauleylab.ucsd.edu/public_datasets/data/amazon_v2/metaFiles2/meta_Musical_Instruments.json.gz)

评论数据提供用户、商品、评分和交互时间。商品元数据提供标题、品牌和类别等内容特征。
评论正文、图片、购买转化率都没有被当作本轮模型效果证据。
元数据是静态快照，无法保证每个字段在过去的推荐时刻都已经可见；这个限制继续保留。

| 处理阶段 | 规模 | 含义 |
| --- | ---: | --- |
| 原始评论 | 231,392 条 | 下载文件内的记录数 |
| 评分过滤、去重和 5-core 后 | 175,848 条；21,363 用户；8,627 商品 | 清洗后的基础数据 |
| 严格时间切分后 | 85,389 条；9,249 用户；8,575 个实际出现的商品 | 最终参与四阶段实验的交互 |
| 召回训练集 | 57,642 条；8,169 商品 | 用于训练协同模型和内容词表 |
| 排序训练、验证、测试 | 各 9,249 条 | 每位合格用户在每阶段各一个目标 |
| 元数据匹配率 | 99.93% | 清洗映射商品中可以找到元数据的比例 |

有 12,114 名用户因为不同时间戳数量不足被排除。数据时间精度和严格切分规则会影响人群范围，
不能把结果推广到所有 Amazon 用户。来源 URL、原文件 SHA-256、过滤行数、切分检查和产物哈希见
[数据清单](../results/musical_instruments_2018/dataset_manifest.json)。

最初也检查了 All Beauty 2023，但现有规则切分后只剩 198 名用户、280 个商品。
用 200 个候选会几乎覆盖整个商品目录，研究价值有限，所以在模型比较前换成乐器品类。

## 三、同协议复现是否成功

复用评分至少 3、用户和商品 5-core、严格时间顺序、完整目录评估、历史商品过滤、
验证集早停、RRF 融合和最终 200 候选等规则。没有根据新测试集重新调参。

Recall@100 可以理解为：对每位用户，把真正的下一件商品放进推荐前 100 件的比例。
Candidate Recall@200 则是看它有没有进入交给排序模型的 200 件商品。
例如 19.68% 表示约每 100 位测试用户，有 20 位的目标商品进入候选集；不是购买率。

| 乐器测试指标 | 结果 |
| --- | ---: |
| 相同候选协议的三通道 Candidate Recall@200 | 17.29% |
| 加入内容后的四通道 Candidate Recall@200 | 19.68% |
| 增加幅度 | +2.39 个百分点 |
| 增幅的 95% 配对置信区间 | +1.92 至 +2.87 个百分点 |
| 严格冷启动：内容 Recall@100 | 10.08%，48/476 命中 |
| 严格冷启动：Two-Tower Recall@100 | 0% |
| 热门推荐 / ItemCF / Two-Tower Recall@100 | 10.95% / 6.83% / 10.00% |
| Two-Tower 与内容融合 Recall@100 | 12.29% |

这里“严格冷启动”指目标商品没有召回训练交互，但允许在商品元数据目录中出现。
置信区间通过对同一批用户的差值重新抽样得到，可以检验提升是否主要由少量用户造成。
四通道独有命中 369 位，三通道独有命中 148 位，净增加 221 位。
详细证据见[内容消融结果](../results/musical_instruments_2018/phase6/content_experiment.json)。

结论：增加内容召回的核心发现，在第二个品类上仍然成立。
但 Two-Tower 单独使用时没有超过热门推荐，不能写成“深度学习在所有数据上都优于传统方法”。
新数据的绝对成绩低于 Video Games 并不构成代码错误，不同品类本来就有不同的可预测程度。

另外重新拟合了全局时间切分模型。2017 年切分后的最终窗口中，5,246 名用户的
协同融合 Candidate Recall@200 为 15.15%，加内容后为 17.04%；差值置信区间为
+1.11 至 +2.67 个百分点。内容命中 32/280 个严格冷启动目标。
这个检查只包含 Popularity、ItemCF 和内容方法，没有使用按另一种切分训练的 Two-Tower。
它验证内容方向的稳健性，不能与四通道结果混称为同一个实验。

### 完整排序流水线

完整排序流水线也在新数据上训练并测试了两份模型。
它保持原排序配置每通道的请求量：双塔 100、ItemCF 100、热门 20，内容版额外请求内容 100，
再融合到 200 个候选。它与上面的“每通道先取 200 个”的召回消融不同，因此候选命中率数值不同。

| 乐器完整流水线测试指标 | 三通道版 | 内容四通道版 |
| --- | ---: | ---: |
| Candidate Recall@200 | 16.27% | 18.41% |
| 原候选顺序 NDCG@10 | 0.73% | 0.91% |
| LambdaRank NDCG@10 | 1.51% | 1.67% |
| LambdaRank Recall@10 | 2.93% | 3.18% |

NDCG 会考虑目标商品排在多靠前的位置，越高越好。
两份排序模型都优于各自的原候选顺序。但内容版相对三通道版的 NDCG 差值只有约
+0.15 个百分点，95% 配对置信区间为 -0.04 至 +0.35 个百分点，包含零。
所以不能说内容版的最终 Top-10 排序提升已经得到可靠验证。
召回改善明确，不等于最终排序必然改善，这是本轮保留下来的重要研究边界。
统计覆盖全部测试用户，召回失败的用户计零；详见
[最终排序配对比较](../results/musical_instruments_2018/paired_ranker_comparison.json)。

## 四、GRU 对照做了什么

原模型把最近的历史商品向量取平均，不保留历史商品之间的顺序。
新模型用 GRU 按顺序读入最近 20 件商品，形成用户历史表示。
用户 ID 向量、商品塔、64 维表示、损失函数、logQ 修正和评估协议继续使用现有实现。
这是 Two-Tower 内部的历史编码器对照，不是完整复现 GRU4Rec，也没有加入 Transformer。

为了公平比较，新训练了一份平均编码器模型。两者使用相同的 seed=42 和训练参数，
最多训练 30 轮，按验证集 Recall@100 选择模型，再进行冻结测试。
这里的平均编码器成绩是新对照，不覆盖以前保存的历史成绩。

| Video Games 测试指标 | 新平均编码器 | GRU |
| --- | ---: | ---: |
| Recall@100 | 9.39% | 10.19% |
| Recall@10 | 1.80% | 2.13% |
| NDCG@10 | 0.85% | 1.07% |
| Top-10 商品覆盖率 | 73.40% | 48.67% |
| 热门偏向比 | 2.25 | 2.85 |
| 模型参数数 | 3,577,984 | 3,602,944 |

主要指标增加约 0.80 个百分点，相对提升约 8.46%；95% 配对置信区间为
+0.34 至 +1.23 个百分点。主要指标的精确 McNemar 检验 p 值约 0.000502。
GRU 独有命中 1,071 名用户，平均编码器独有命中 915 名用户。

覆盖率是所有用户前 10 件推荐合起来覆盖了训练目录的多少商品。
热门偏向比越高，推荐越集中于交互次数多的商品。
因此 GRU 的召回改善伴随着多样性下降，这不是全面优于原模型。
而且它的 Recall@100 仍低于 ItemCF 的 15.70%。

结论：这个模型对照符合“增加模型类别研究证据”的预期，但不足以支持直接替换现有服务。
目前只比较了一个随机种子；用户配对置信区间不能代替多种子稳定性检查。
两者参数量也不完全相同，不能把全部差异都归因于顺序建模。
训练同时运行了其他实验，因此训练日志中的时长不用于公平速度对比。
证据见[GRU 配对比较](../results/video_games_2018/sequence/paired_comparison.json)。

## 五、工程实验如何理解

服务测试比较 1、2、4 个 Uvicorn 进程，在并发 1、5、10、20 下每组重复 3 次、每次 100 个请求。
关闭 Redis，每个进程限定一个数值计算线程，使用原内容版服务和相同的 100 个已知用户。
记录吞吐量、P95 延迟、失败率和进程内存总量。测试在训练结束后进行。

吞吐量 QPS 是每秒完成多少次请求；P95 是 95% 请求可以在多长时间内完成。
多进程可能提高吞吐量，也会复制部分模型和索引占用更多内存。
内存指标是各进程 RSS 相加，可能重复计算共享页面，不能当作独占物理内存。

商品目录扩展实验另外生成 64 维模拟向量，比较约 1.4 万、10 万、100 万条的
FAISS 精确索引。每种规模进行 50 次预热后的 Top-100 搜索。
这只能衡量索引计算和存储成本，不代表完成了百万真实商品推荐训练，
也不代表百万商品的端到端服务延迟或准确率。

### 工程测量结果

机器为 Windows、20 个逻辑 CPU、约 15.73 GiB 物理内存，使用 PyTorch 2.12.1+cpu 和 FAISS 1.14.3。
3,600 次正式请求全部成功。下表取三次测量的中位数，P95 是每轮 P95 的中位数，
不是把所有请求合并后的 P95，也不是性能置信区间。

| 同时 20 个请求 | QPS 中位数 | P95 中位数 | 进程 RSS 合计中位数 |
| --- | ---: | ---: | ---: |
| 1 进程 | 19.04 | 1,401 毫秒 | 845 MiB |
| 2 进程 | 30.79 | 901 毫秒 | 1,697 MiB |
| 4 进程 | 35.11 | 886 毫秒 | 3,341 MiB |

4 进程相对 1 进程的吞吐量约为 1.84 倍，P95 降低约 36.75%，内存合计约为 3.96 倍。
所以工程方向符合“并发下有收益”的预期，但不是增加 4 倍进程就获得 4 倍速度。
4 进程在并发 20 的三次 QPS 为 28.11 至 36.71，存在明显波动。
并发 1 时它反而更慢；并发 10 时，它的 P95 也不如 2 进程。
因此本地实验下 2 进程是值得考虑的内存和吞吐折中，不能据此规定生产环境参数。
本轮没有修改 AWS 或 Docker 的运行配置。

| 模拟向量目录 | 单次索引搜索 P50 | 单次索引搜索 P95 | 序列化索引体积 |
| --- | ---: | ---: | ---: |
| 13,923 条 | 0.48 毫秒 | 0.62 毫秒 | 3.40 MiB |
| 100,000 条 | 6.22 毫秒 | 10.74 毫秒 | 24.41 MiB |
| 1,000,000 条 | 102.75 毫秒 | 127.29 毫秒 | 244.14 MiB |

百万规模的精确索引能够运行，但检索耗时明显上升。后续若使用大规模真实商品数据，
需要再比较近似索引的速度和召回精度。这里没有完成那个比较。
244.14 MiB 只指索引文件，原始向量、计算临时空间和完整模型的内存另算。
机器上其他应用、调度、温度和固定测试顺序也可能影响耗时。
详细原始测量见[扩展性结果](../results/video_games_2018/scaling/scaling.json)。

### 是否符合预期

跨品类内容召回：符合，且配对区间和全局时间检查支持同一个方向。
GRU 对照：召回改善符合，但多样性下降，只形成研究证据，不替换已发布模型。
工程扩展：高并发下改善符合，同时公开内存增加和低并发退化。
完整排序：平均值改善，但统计证据不足，不能宣传为已经证实的提升。

目前仍缺少跨独立来源的数据验证、GRU 多随机种子、参数量匹配对照、
更长时间的随机顺序压力测试、近似索引精度比较以及真实线上业务结果。
对申请材料而言，本轮强化的是实验设计、统计分析、复现和工程测量能力，不能写成达到 SOTA。
